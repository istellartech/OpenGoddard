GitHub Pagesで動かす最適制御教材の設計案
========================================

この文書のReact/SVG案は将来の拡張案です。初期公開はAGENTS.mdのMatplotlib動画生成方針を優先します。

これは今後の実装計画です。現時点でサイト、ブラウザ再生器、データ一括生成器、
Pagesへのデプロイ処理は実装していません。2026-10-18時点のサンプルと公開方針に基づきます。

基本構成
--------

**Pythonで解く → 検査したJSONを保存 → ブラウザで再生・比較する** 構成を第一段階にします。
GitHub PagesはHTML・CSS・JavaScriptの静的ホスティングなので、閲覧時にPythonサーバーを
起動する設計は採りません。この公開形態は
`GitHub Pages公式説明 <https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages>`_
に対応しています。

AGENTS.mdの候補に沿い、解説・コード・APIリファレンスはAstro + Starlight + MDX、
再生パネルはReactのコンポーネントとする案です。2次元の教材から始めるので、描画は
SVGを第一候補にします。軌道・物体・推力矢印・グラフのカーソルを同じ時刻で動かします。
大きなデータや多数の物体が必要になったら、その描画部分だけCanvasを検討します。

Reactコンポーネントをページに埋め込み、表示されたときに動作を有効にする構成が可能です。
`AstroのReact統合 <https://docs.astro.build/en/guides/integrations-guide/react/>`_ と
`clientディレクティブ <https://docs.astro.build/en/reference/directives-reference/#clientvisible>`_
を使い、最初は静的な図と説明を表示し、画面外の教材まで一度に読み込まないようにします。
Python API文書の自動生成は別の必須要件で、候補のstarlight-pydocs + Griffeについては
既存docstring・数式・相互参照・抽出結果の検証を先に行います。

パラメータ操作は何をするのか
--------------------------

第一段階のGUIは **事前に計算した条件を選んで、対応する解を表示する** ものにします。

* 再生時刻、再生速度、軌道の重ね合わせ、グラフの表示項目はブラウザで自由に変えられます。
* 距離、推力上限、床の深さなどは、あらかじめ用意したケースを選びます。
  スライダーを使う場合も計算済みの値にスナップし、選択中の実際の値を表示します。
* 複数パラメータの組み合わせはマニフェストに存在するものだけ選択可能にします。
  存在しない組み合わせを近いケースで黙って置き換えないようにします。

異なる最適解を混ぜて中間パラメータの「解」を合成すると、運動方程式や制約を満たすとは
限りません。特に定速区間の出現や床への接触で区間構成が変わるため、ケース間の数値補間を
再最適化の代わりには使いません。区間内の再生時刻に対する補間とは分けて扱います。

任意の数値を入力して再最適化する機能が必要になった場合は、ブラウザ内Pythonか外部の
求解APIを別途比較します。前者はNumPy・SciPy・対象Python版・ソルバーの対応と計算時間、
後者はホスティング、計算量制限、待ち時間、運用を検証する必要があります。初期公開には
含めず、現在のParametersとsolveの入口をそのときにも再利用します。

最初に公開する3題
-----------------

.. list-table:: 表示と比較する条件
   :header-rows: 1

   * - 番号 / 安定したID
     - 動かすもの
     - 同期表示するグラフ
     - 条件比較
   * - 02 / move_stop
     - レール上の物体と加速度矢印
     - 位置・速度・加速度
     - 最短時間と最小二乗操作量、速度上限、加速度上限
   * - 04 / constrained_descent
     - 軌道上の球と床
     - 深さ・速さ・軌道角
     - 床なし、接しない床、浅い床、重力
   * - 09 / soft_landing
     - 機体高度と推力に応じた噴射表示
     - 高度・速度・推力・質量
     - 初期高度、最大推力、質量一定と質量変化

推力表示は向きと大きさを伝える図とし、噴射画像の大きさに数値上の意味があるか明示します。
グラフの単位・縦軸方向は既存JSONのunitsとcoordinatesに合わせます。

例題の番号と公開データの識別
--------------------------

``examples/catalog.py`` を学習順序の一覧とし、番号は表示にだけ使います。
将来のURLとJSONの識別には ``move_stop`` などの安定したIDを使います。
たとえばサイトでのページを ``/OpenGoddard/examples/move_stop/``、データを
``/OpenGoddard/data/trajectories/move_stop/speed-limit-2.json`` とする案です。
順序が変わってもデータとページの識別子を変える必要がありません。

現在は02・04・09が共通のParameters / make_problem / solve / plot / JSON出力に対応します。
残り12例は番号と保存先を整理した従来形式です。上昇・段分離・軌道遷移のアニメーションを
作る前に、必要な例から同じデータ出力の入口を加えます。全15例がすでに共通の出力APIを
持っていると仮定してサイトを作らないようにします。

データ生成とマニフェスト
----------------------

将来の一括生成器は、表示したい条件を明記した設定を読み、次の順に処理します。

1. 安定した例題ID、ケースID、Parameters、ノード数を読み込む。
2. 求解し、solver.successとノード間の誤差・経路制約・終端条件を検査する。
3. 比較用の細かいメッシュでも時間・目的値・主要な物理量の変化を検査する。
4. 検査を通ったケースだけ、再生用JSONと一覧のmanifest.jsonをまとめて書き出す。

同じParametersでもノード数などで結果が変わるため、ケースの生成条件も記録します。
マニフェストには次の情報が必要です。これは今後追加する仕様で、現行のJSONに
すべて実装されているわけではありません。

* 例題ID・ケースID・表示名・使用する描画器、Parametersの実値。
* 選択可能なパラメータの値と、存在する組み合わせの一覧。
* データへの相対パス、schema_version、単位、物理的な所要時間・目的値。
* ノード数、再生用サンプル数、誤差指標、検査の許容値と合否。
* ソースとパラメータのハッシュ、依存関係の固定情報、生成手順の版。

ケースを切り替えた際は必要なJSONだけを読み込みます。大きな全条件データを
初期JavaScriptに埋め込まず、マニフェストにある相対パスから取得する構成です。
出力は一時ディレクトリで完成させてから一式を置き換え、古いケースの混入を避けます。

現行のtrajectory JSONはschema_version=1で、パラメータ・単位・座標の説明・求解状態・
誤差指標・参照解・区間ごとのnodesとsamplesを持ちます。マニフェストはその外側に置き、
個別ケースを ``solve(...).write_json(...)`` で再現できる関係を維持します。
イベント、表示用座標変換、厳密な型定義が必要になった時点でスキーマを拡張し、
既存v1の読み込みとの互換性を明記します。

再生器の時刻と区間境界
--------------------

再生器は例題ごとに共通のプレーヤーを使い、描画だけを差し替えます。

* 再生・停止、シーク、速度変更、最初に戻る、区間境界への移動。
* 実時間tと進行率t/tfの表示。同時比較は実時間と進行率のどちらに揃えるか選ぶ。
* requestAnimationFrameの経過時間から物理時刻を計算し、画面のフレーム数に依存させない。
* samples内では時間について線形補間し、区間をまたいで高次補間しない。
* 境界の同一時刻に異なる制御値がある場合は、次の区間を選ぶ規則を一貫させる。
* 3つの新教材では状態は連続。将来の段分離では質量が跳ぶため、区間境界の前後を
  別の状態として保存し、質量の跳びを滑らかにつながない。

複数軌道の比較では同じ物理スケールの軸を使うか、正規化したことを明示します。
各例のsolver.objectiveはモードにより正規化が異なるので、画面には物理単位の所要時間、
力積、推進剤消費、二乗操作量などを、名称と単位を付けて表示します。

キーボードで操作できるボタンとスライダーを用意し、自動再生は既定でオフにします。
動きを減らす設定にも対応し、静的な軌道図と主要な数値は再生なしでも読めるようにします。

サイトとGitHub Pagesの配置案
--------------------------

将来、既存のdocs/・docs_sphinx/とは別の ``website/`` を作る案です。

.. code-block:: text

   examples/
     catalog.py                    # 順序・安定したID（実装済み）
     _shared.py                    # 結果出力・CLIの共通補助処理（実装済み）
     01_minimum_energy_transfer/    # 以下、15例すべて1例題1フォルダ
       main.py                     # 実装と実行入口（実装済み）
       README.rst                  # 例題ごとの説明（実装済み）
     ...
     14_polar_tsto_taiki/
       main.py
       README.rst
       data/                       # この例の入力CSV
     # 各例題の参考図はfigures/、生成物はoutput/（Git対象外）
   website/                        # 以下は今後の実装案
     src/content/docs/examples/    # 数式・コード・結果を説明するMDX
     src/components/trajectory/    # プレーヤー・グラフ・3種類のSVG描画器
     public/data/trajectories/     # Pythonで生成したJSONとマニフェスト
     astro.config.mjs

公開先は ``https://istellartech.github.io/OpenGoddard/`` を前提とし、
``site: 'https://istellartech.github.io'``、``base: '/OpenGoddard'`` とします。
AstroのGitHub Pages向け手順でも、プロジェクトサイトにはリポジトリのbase設定が必要です。
`Astro公式のPages公開手順 <https://docs.astro.build/en/guides/deploy/github/>`_
に沿って設定します。

JSONを ``/data/...`` とルート絶対パスで取得するとプロジェクトの接頭辞が抜けるので、
ブラウザ側はベースURLを通じてパスを組み立てます。将来の実装例は次の形です。

.. code-block:: javascript

   const base = import.meta.env.BASE_URL.replace(/\/?$/, '/');
   const manifest = await fetch(`${base}data/trajectories/manifest.json`);

将来のActionsでは、Python環境の準備 → テスト → ケース求解と検査 → API文書生成 →
Astroビルド → 公開用成果物の確認 → Pages公開、の順にします。求解や検査に失敗した
データを公開成果物に混ぜません。検査に成功した静的データの公開なので、訪問者ごとに
最適化を実行するサーバーは必要ありません。

API文書の出力品質と既存URLの移行を確認するまでは、既存docs/やdocs_sphinx/を
削除・置換しません。既存Sphinx文書へのリンク・リダイレクトを含めて移行を決めます。

実装の順序と完了条件
------------------

1. **データを揃える**：3教材の代表ケースを一括生成し、型とマニフェストを定義する。
   同じ条件を再現でき、検査失敗を公開候補から除外できること。
2. **02だけで再生を成立させる**：物体・3グラフ・シーク・ケース選択を同期させる。
   再生速度を変えても同じ物理時刻で同じ位置になり、加速度の切り替えが保存されること。
3. **04と09へ広げる**：深さ軸の向き、床への接触、推力と質量を検証する。
   重力変更で形状を保つケースと、推力変更で軌道が変わるケースを比較できること。
4. **解説・APIと統合する**：Astro/StarlightとAPI生成の互換性を検証して統合する。
   数式、実装、グラフ、状態の対応を同じページで確認できること。
5. **/OpenGoddard/で試験して公開する**：トップへのアクセスだけでなく、例題ページを
   直接開く、再読み込みする、JSONを取得する、スマートフォンとキーボードで操作する、
   シークして境界を跨ぐ、読み込み失敗を表示する、といった流れを確認する。

この段階の後に、既存の上昇・段分離・軌道遷移を必要な順で共通APIに移し、同じ
プレーヤーを使える描画器とデータを足します。15例の番号整理と、15例すべての
ブラウザ再生対応は、別々の完了条件として扱います。
